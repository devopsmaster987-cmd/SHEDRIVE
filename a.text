## 1. Product summary

- Women-only ride-hailing: riders and drivers are both women.
- At signup, a selfie is captured and sent to a Python face-verification microservice that returns a gender prediction with a confidence score.
- Confidence >= 0.85 and predicted female: auto-approve. Otherwise: status `pending_review` and an entry in the admin review queue (ID document fallback).
- The model is a first-pass filter only. Automated gender classification is not 100% accurate, and the manual admin review fallback is a deliberate design decision. Reflect this in code comments, the README, and the UI copy (for example "Your account is under review" rather than "Rejected").
- Privacy by design: **raw selfies are never stored long-term**. Process in memory, store only the numeric face embedding and the verification result, then discard the image.
- Fare negotiation: rider proposes a price, drivers accept or counter-offer, rider picks.
- Safety features: live trip tracking, SOS button, emergency contacts.

## 4. Face verification service (build first, it is the riskiest part)

**Endpoints**
- `POST /verify` accepts multipart image (`selfie`, max 5 MB, JPEG/PNG only). Returns:
  ```json
  { "face_detected": true, "gender": "female", "confidence": 0.92,
    "decision": "auto_approved | needs_review | no_face",
    "embedding": [ ...floats... ] }
  ```
- `GET /health`
- `GET /metrics` (Prometheus)

**Logic**
- Use `DeepFace.analyze(img, actions=["gender"], enforce_detection=True)` for gender and confidence. Normalize the confidence to 0-1.
- Use `DeepFace.represent(...)` (for example Facenet) for the embedding.
- Decision rules, with thresholds configurable via env (`CONF_THRESHOLD=0.85`):
  - no face or multiple faces: `no_face`, ask the user to retake
  - predicted female and confidence >= threshold: `auto_approved`
  - anything else: `needs_review`
- Process the image **in memory only**. Do not write it to disk or log its contents.
- Validate file type and size, return clear 4xx errors, and set a timeout.
- Preload the model at startup so the first request is not slow.
- pytest tests with a few sample images and mocked DeepFace for fast unit tests.

## 5. Backend (Node.js + Express)

**Conventions**: REST under `/api`, JSON responses `{ success, data, error }`, central error handler, request validation (Joi or express-validator), `helmet`, `cors` with an allowed-origin env var, `express-rate-limit` on auth routes.

**Models (Mongoose)** (fields from my design doc):
- `User`: name, email, phone, passwordHash, role (`rider|driver|admin`), faceEmbedding, verificationStatus (`pending|approved|pending_review|rejected`), phoneVerified, emergencyContacts[], createdAt
- `DriverDetails`: user, vehicleType, plateNumber, licenseDocUrl, ratingAvg, isOnline, currentLocation (GeoJSON Point with 2dsphere index)
- `Ride`: rider, driver, pickup, drop (GeoJSON), distanceKm, offeredPrice, finalPrice, status (`searching|accepted|arriving|in_progress|completed|cancelled`), timestamps
- `RideOffer`: ride, driver, offerPrice, status (`pending|accepted|rejected|countered|expired`)
- `Payment`: ride, amount, method (`cash|wallet`), status
- `Rating`: ride, ratedBy, ratedUser, stars (1-5), comment
- `SOSAlert`: ride, user, location, timestamp, status (`open|acknowledged|resolved`)
- `AdminReviewQueue`: user, faceConfidenceScore, submittedDocs[], status, reviewedBy, reviewedAt, note
- `Notification`: user, message, readStatus
- `WalletTransaction` (simple wallet ledger)

**Key flows and endpoints**
- Auth: `POST /api/auth/signup` (multipart: fields + selfie, plus license doc for drivers), `POST /api/auth/verify-otp`, `POST /api/auth/login`, `GET /api/auth/me`.
  - Signup calls the face service (`faceClient`), applies the decision, sets `verificationStatus`, creates an `AdminReviewQueue` entry when needed, discards the selfie, and stores only the embedding.
  - Users with status `pending_review` or `rejected` cannot book or accept rides (enforce in middleware).
  - If the face service is down, fail safe: put the user in `pending_review`, never auto-approve.
- Rides: create ride request with offered price, list nearby drivers (Mongo `$near`), cancel, complete, history.
- Offers: drivers accept or counter-offer, rider accepts one offer, expire stale offers.
- Drivers: toggle online/offline, update location, earnings summary.
- Payments and wallet: mock wallet top-up and ride payment (no real gateway).
- Ratings: both sides rate after a completed ride; recompute driver `ratingAvg`.
- SOS: create alert (notifies emergency contacts via the notification service mock and flags admin), list for admin.
- Admin: stats, user/driver list, ban/suspend, review queue (approve/reject with note), driver document review, SOS list.
- Seed script: creates an admin user, sample riders and drivers.

**Socket.IO events** (JWT-authenticated handshake, rooms per ride)
- `driver:location` (driver to server, throttled), `ride:request` (server to nearby drivers), `offer:new`, `offer:accepted`, `ride:status`, `ride:location` (live position to rider), `sos:triggered` (to admin room).

**Metrics**: `prom-client` default metrics plus an HTTP request duration histogram, request counter, and gauges for active socket connections and online drivers, all exposed at `/metrics`.

### 6A. 3D and visual design direction

**Concept: "Neon Midnight City."** A glowing, cinematic, futuristic night-city world that feels safe, powerful, and feminine without being cliché. The visitor is flying through a living 3D city at night where every route is lit up.

**Look and feel**
- Dark immersive base (deep midnight indigo/black) with a vivid gradient accent palette: electric magenta, hot pink, violet, and cyan glow. Define all colors, spacing, radii, and shadows as CSS variables in one design-system file.
- Glassmorphism panels (blurred translucent cards with thin glowing borders), soft neon bloom, grain overlay, and subtle chromatic aberration on hero transitions.
- Typography: bold oversized display font (for example Space Grotesk, Clash Display, or Syne) paired with a clean body font (Inter). Huge kinetic headlines with split-text letter and word reveals.
- Custom magnetic cursor with a glowing trail on desktop; tactile hover states and micro-interactions on every button and card.
- Animated gradient mesh and floating particle backgrounds on non-3D sections.

**3D requirements (Three.js)**
1. **Landing hero**: a full-screen 3D night city built procedurally (instanced buildings with emissive window lights, fog, bloom post-processing via `EffectComposer` + `UnrealBloomPass`) with a stylized glowing car driving along neon road lines. The camera moves with scroll (GSAP ScrollTrigger scrubs a camera path) and reacts to mouse parallax.
2. **Signup face-capture step**: a futuristic 3D scanning effect around the live camera feed (rotating holographic rings, scan-line shader sweeping across the face frame, particle burst on success, a distinct but kind animation for "under review"). It must never look like rejection.
3. **Book a Ride**: a tilted, pitched 3D map (MapLibre GL with extruded 3D buildings, or a Three.js city layer synced to coordinates) with glowing animated route lines, pulsing pickup and drop pins, and nearby drivers shown as moving glowing 3D car markers.
4. **Searching for driver**: radar-pulse shader with orbiting particles; offers fly in as 3D floating cards with spring physics.
5. **Live tracking**: the car model moves smoothly along the route with interpolated Socket.IO positions, a light trail behind it, and a camera that can follow it. SOS button is a pulsing glowing 3D orb that expands into a full-screen red alert shader when triggered (with a confirm step to prevent accidents).
6. **Ride summary and rating**: a celebratory scene with confetti or particle fireworks, and stars as 3D objects that light up one by one.
7. **Dashboards (driver and admin)**: 3D-styled analytics: animated counters, 3D bar/globe or glowing line charts (Three.js or Chart.js with custom styling), a rotating globe or city map showing live online drivers and SOS alerts.
8. **Every page transition**: cinematic transitions (a shader wipe or a camera fly-through), never a plain page reload feel. Add a branded animated 3D loader and a preloader that shows asset progress.

**3D asset rules**
- Prefer **procedural geometry and shaders** so there are no heavy asset downloads. If a glTF car model is used, keep it under about 1.5 MB, compress with Draco or meshopt, and load lazily.
- Use instancing for buildings and particles. Cap pixel ratio at 2. Dispose of geometries, materials, and textures when leaving a page.
- Target 60 fps on a mid-range laptop and a smooth 30+ fps on mid-range phones.

**Performance, accessibility, and fallbacks (required, not optional)**
- Detect WebGL support and low-power devices; fall back to a lighter static-gradient or 2D version with the same layout. Provide a "Reduce effects" toggle in settings.
- Respect `prefers-reduced-motion` (disable parallax, camera moves, and large animations).
- Text must keep WCAG AA contrast on glass panels. All forms, buttons, and the SOS control must be fully usable by keyboard and screen readers; the 3D canvas is decorative and gets `aria-hidden`.
- Core functions (login, booking, SOS) must work even if 3D fails to load.
- Code-split per page (dynamic imports), lazy-load Three.js only on pages that need it, and compress textures. Aim for Lighthouse Performance 80+ on desktop.
- Mobile-first layouts: the 3D scenes must adapt to portrait screens, with touch controls instead of mouse parallax.
